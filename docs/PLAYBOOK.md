## 2. 稳定的工程实践（与实验结论无关，先行遵守）

| 实践 | 原因 |
|---|---|
| 同种子配对 + 按关聚合 | 关卡间三星率 0–100%，pooled 方差被难度主导 |
| 50 seeds/关做确认、24 seeds 做筛选 | 见 `EVAL_PROTOCOL.md` §3 功效估算 |
| prompt「稳定前缀 + 动态尾」 | 缓存命中价 ¥0.02/M vs 不命中 ¥1/M（50×） |
| 只输出动作 ID，不输出解释 | 输出 ¥4/M，是缓存输入的 200× |
| 跳过只有一个合法选项的决策 | 减少 30–50% 调用 |
| 每条技能带 `conditions` 元数据 | 检索与「激活」统计都需要，但不参与执行 |
| 记录 `prompt_hash` / `library_version` | 事后归因与断点续跑（**当前 runner 只落 `library_version` 与 loadout hash，未落 prompt_hash**） |
| `--seeds` 从 1 起，禁用 0 | 引擎 minstd LCG 的 0 是吸收态，首轮 8 骰恒为 CRYO |
| 卡池 = 引擎内置（`configs/engine.lock`），不 pin 旧版本 | 唯一可用资产目录是 latest，pin 会造成卡面/费用/血量错配 |
| prompt 样本必须来自 `GITCG_LLM_TRACE` 的 `messages` | 二次渲染会与真实调用漂移，无法审计 |
| 抽取 `max_tokens≥32768`，length 时翻倍重试一次 | reasoning 与正文共享预算，8192 会稳定截断到 0 候选 |
| 抽取候选不得改写全局 strategy（单关归纳 → stage_specific） | 全局策略手工维护且无 `conditions.stages` pin；单关建议一旦覆盖会注入所有关卡（见 `docs/failures/extract-overwrote-global-strategy.md`） |

## 3. 候选方法（未验证）

| 候选 | 设计 | 判据 |
|---|---|---|
| 库级配对 A/B 门控 | v_{n+1} vs v_n 同种子配对 | 三星率 Δ 的 CI 下界 > 0 |
| 批量更新（每 20 局） | 对比每局更新 / 每 20 局 / 认证门控 | 库大小 vs 三星率 |
| 检索 top-k | 1/3/5/8 | 三星率与 token/局 |
| 技能表示 | 自然语言 / 结构化 JSON / 两者 | 检索命中率、引用率 |
| 分层技能（规则/策略/关卡特化） | 特化层优先匹配 | 留出关卡上的迁移 |
| 激活日志裁撤 | 零激活 200 次或消融为负 → retired | 库精度、三星率 |

## 4. 不要做的（来自上游负结果，见 `docs/failures/`）

- 不要用「整局胜负」当技能筛选信号（上游 matchup 重加权/胜局筛选 −0.14）；
- 不要用 LLM 自评决定技能去留（上游 search-as-teacher 与自评门控均无效）；
- 不要跨关平均「星数」（目标数 1–3 不等，不可比）。
